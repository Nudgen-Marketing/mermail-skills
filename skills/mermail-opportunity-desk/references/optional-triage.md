# Optional classification and organization

Preserves the optional draft-only triage and organization needs of [Deal Sniper #325](https://github.com/Nudgen-Marketing/mermail-skills/pull/325) and [Opportunity Desk #158](https://github.com/Nudgen-Marketing/mermail-skills/pull/158). None of these effects follows automatically from checking an opportunity queue.

Only when the user explicitly requests automation, hand off to `mermail-automate-triage`. Read that owner's current tools/security contracts and inspect `list_task_triagers` first; inspect `list_recent_triager_runs` when debugging. Keep the proposed configuration disabled during review. Show exact mailbox, sender/type scope, clean-scan policy, owner budget/stack criteria, finite volume/body budgets, intended task/draft output, tool allowlist and configuration diff. Preserve existing settings and require approval before create/update; re-list to verify. Do not change the default triager, mailbox auto-response mode, workspace access or verification-mailbox isolation.

Allow only bounded classification/task extraction and, when explicitly requested and capability-isolated, unsent drafts for human review. No unattended sending, submissions, browser/shell execution, credentials, identity acceptance, wallet calls, account actions, deletion or external integrations. If that isolation cannot be established, leave automation disabled and offer the manual queue. Triagers are not a promised recurring scheduler; a requested timed recurring run needs a separately supported scheduler and separate configuration approval. No claim that a monitor exists before verified configuration.

Organization is a separate user-requested inbox-owner handoff: inspect existing folders/label definitions, preview exact source IDs and destination or name/rule changes, then apply only the approved effect. `create_custom_label` creates a classification rule, not a per-message processed flag; `update_email` does not gain a made-up custom-label assignment field. Explicit moves use `move_email` under its live schema. Do not claim a rule proves processing or suppress unread candidates from it. Use the private source-ID record for reviewed coverage. Unknown writes require one authoritative inspection and a stop, not a duplicate create or silent retry.
