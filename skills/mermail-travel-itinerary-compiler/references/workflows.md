# Workflows

The end-to-end sequence this skill drives, plus the canonical branches for re-runs, conflicts, and degraded parses. Pair with [SKILL.md](../SKILL.md) (the 13-step Workflow), [tools.md](tools.md) (MCP argument envelopes), and [security.md](security.md) (binding safety rules).

## Phase 0 — Intent and scope

The user request must resolve to:

- `date_range` (default `today` to `today + 90d`)
- `categories` (default `flight`, `hotel`, `car`, `restaurant`, `activity`)
- `home_tz` (default workspace TZ, else mailbox TZ)
- `trip_label` (default derived from the dominant destination city)
- `version` (default `1`; increments only on re-run with new mail)

Pause and ask if any decision-critical value is missing. Do not enter discovery without a complete scope.

## Phase 1 — Discovery

Resolve the mailbox and run five parallel vendor sweeps. See [tools.md](tools.md) for the canonical `search_emails` payloads.

If the sweep produces fewer than three candidates and the date span is wider than 30 days, run the `list_emails` fallback once with `limit: 200` and the same safety filters.

State after phase 1: `discovering` → `filtered`.

## Phase 2 — Fetch and extract

For each survivor, fetch the body with `get_email` (`max_body_chars: 10000`, `agent_safe_content: true`). On `content_omitted: true`, mark the booking `low` and exclude from the timeline.

Extract the per-category fields defined in the **Booking Model** section of [SKILL.md](../SKILL.md#booking-model). Tag every item `high`, `medium`, or `low`.

State after phase 2: `extracting`.

## Phase 3 — Normalize, group, and conflict-detect

Normalize every start and end to:

- `start_local` plus `start_tz` (IANA)
- `start_utc` (ISO 8601, second precision)
- `end_local` plus `end_tz`
- `end_utc`

Sort all bookings by `start_utc`. Group into `Trip`s: a candidate joins the current trip when its `start_utc` is within 48 hours of the prior item's `end_utc`, else start a new trip.

Detect the five conflict types from [SKILL.md](../SKILL.md#conflict-rules). Each conflict becomes one entry in the conflict report with the offending items and a one-line summary.

State after phase 3: `normalized` or `conflict_detected`.

## Phase 4 — Render

Produce three artifacts:

1. **HTML timeline** — table-based, 720px max width, category color left border, vendor footer in muted color, hidden `<details>` block wrapping a `<pre>` JSON object. Footer text: `Generated by Mermail Travel Itinerary Compiler · v1`.
2. **Plain-text timeline** — ASCII, day headers in `home_tz`, per-item local time plus UTC offset, confirmation and vendor on the next line.
3. **Hidden JSON** — full `Trip` and `Booking` list, conflicts, audit counts.

Optionally attach the `.ics` file when the host supports `attachments` on `save_draft`.

State after phase 4: `rendered`.

## Phase 5 — Save and ask

Call `save_draft` with `idempotencyKey: sha256(trip_id + ":" + version)`. Record the returned `draft_id`.

Present the user-facing preview:

- Trip name, date range, home TZ
- Recipient
- Item count and conflict count
- Unverified count
- Draft subject and `draft_id`
- Next required action: `awaiting_approval`, `awaiting_edit`, `awaiting_send`, or `awaiting_schedule`

State after phase 5: `drafted` → `awaiting_approval`.

## Phase 6 — Send or update

If the user approves exactly:

- call `send_email` once with the same idempotency key and the approved payload snapshot

If the user requests an edit:

- re-save the draft with `version + 1` and a new idempotency key
- re-enter Phase 5 preview

If the user cancels:

- leave the draft untouched
- report `state: awaiting_user` with the next required action

If the host restricts the profile to `agent-inbox`, the save is unavailable. Surface `state: blocked` with the reason and route the user to a full-profile install.

State after phase 6: `sent`, `scheduled`, `rate_limited`, `unverified`, `blocked`, or `awaiting_user`.

## Re-run branches

### Same version re-run

User asks for the same compile again. Reuse the existing draft and the same idempotency key. Do not create a parallel draft.

### New mail re-run

User reports a new confirmation mail arrived. Re-run the sweep, normalize the new item, and re-save with `version + 1`. The previous draft stays untouched and visible.

### Edit request

User asks to remove a booking, change a recipient, or rename a trip. Re-run the sweep without the diff, re-render, and re-save with `version + 1`. Surface a fresh preview and require fresh approval.

### Cancel

User cancels the compile before any external effect. Leave the draft untouched, log `state: cancelled`, and report the next required action.

## Conflict branches

| Conflict | Branch |
| --- | --- |
| Overlap flight | Include both items in timeline, surface conflict in hidden block, do not reorder automatically |
| Late hotel | Include both items in timeline, surface conflict in hidden block, suggest earlier hotel or later flight in plain text |
| Wrong-city restaurant | Exclude the restaurant from the timeline, surface in unverified list, surface in hidden block |
| Ground gap | Include both items in timeline, surface conflict in hidden block, suggest adding a transport item |
| Stale confirmation | Exclude the booking, surface in unverified list, surface in hidden block |

## Degraded-parse branches

| Symptom | Branch |
| --- | --- |
| Vendor parser fails | Keep email-extracted fields, set `attachment_degraded: true`, continue |
| `content_omitted: true` | Mark `low` confidence, exclude from timeline, surface in unverified list |
| `sender_authentication.status: unknown` | Surface in unverified list, exclude from timeline |
| Vendor not in allowlist | Surface in unverified list, exclude from timeline |
| Idempotency key collision | Surface as `state: ambiguous`, stop, require user direction |
| `email_send_recipient_limit_exceeded` | Stop, require newly approved recipient set |
| `email_send_rate_limit_exceeded` | Surface `Retry-After`, do not replay automatically |
| `email_send_rate_limit_unavailable` | Fail closed, leave draft untouched |

## Output states

The user-facing state vocabulary: `awaiting_scope`, `discovering`, `filtered`, `extracting`, `normalized`, `conflict_detected`, `rendered`, `drafted`, `awaiting_approval`, `awaiting_edit`, `awaiting_send`, `awaiting_schedule`, `sent`, `scheduled`, `rate_limited`, `unverified`, `blocked`, `awaiting_user`, `cancelled`, or `delivery_unknown`. Each state names the next required action.
