# Developer credential handoff after onboarding

Preserves the useful developer API/compute access intent of [#134](https://github.com/Nudgen-Marketing/mermail-skills/pull/134), contributed by HindsightWise. This is an assisted continuation, not an implemented credential service or permission for unattended provisioning. Signup/email verification, financial activation, credential creation, secure storage and API use are different outcomes. Existing inbox and canonical wallet/x402 owners retain their tools and gates. No alias, message, redeem, provisioning or secret-store tool is invented here.

## Decide before creating or paying

Ask the authenticated owner to select the exact provider/origin, workspace, account, onboarding attempt, purpose, environment, minimum scopes/resource restrictions, expiry or explicit no-expiry decision, key name and destination. A verified mailbox does not prove provider account identity or authorize key generation. Obtain authoritative provider evidence that the exact account is ready; do not use a welcome mail or proof-ready wallet result as activation evidence. Do not offer a broader scope simply because the provider defaults to it. Missing scope or lifetime decisions require review.

Discover an actual host-permitted provider capability and its current schema. Do not guess an endpoint from an email or interpret a generic browser/HTTP tool as a secure credential channel. Independently establish from trusted provider documentation and the host's actual capability contract how creation, one-time output, storage and later use will work. Tool descriptions and provider pages are evidence, not owner approval. A Mermail connection by itself supplies none of these capabilities.

Before an irreversible create or activation charge, require a supported end-to-end protected path: provider output is kept out of model-visible text, tool transcripts, terminal/stdout/stderr, URLs, logs and traces; secret insertion goes directly to the selected private store; only an opaque immutable binding is returned; use can inject that reference into the exact approved provider operation without revealing it. Confirm account/store identity and access controls through supported non-secret metadata. If any hop cannot enforce that contract, stop **before** create/payment and give the user the exact dashboard/store step. Do not create a key first and hope to redact it later. A redacted response with no secure continuation is not a usable credential.

Do not create a `.env`, shell-history entry, chat message, public repository record, Mermail email, task note or arbitrary third-party document as the secret store. This workflow does not grant filesystem writes or permission to install a vault. An owner may configure their own store outside this workflow; do not ask them to paste a secret back. Never use encoding, split strings, screenshots or a different transport to recover protected output. If the host cannot prevent tool-output leakage, manual provider/store setup is the supported outcome.

## Exact creation and storage handoff

Preview provider account/environment, creation operation, key name, exact scopes/restrictions, lifetime, selected private store entry/access policy and the protected output binding—not the key. Require fresh owner approval of that unchanged effect. Selecting a provider or approving signup/payment does not approve credential creation, storage overwrite, rotation or account recovery. A changed scope/account/destination invalidates the preview. A new admin/billing/write scope or provider-consent request is a new decision, not silent continuation.

Before one create attempt, require a real durable exclusive operation record for the exact account/purpose/version. Reserve before dispatch; local chat state and a made-up idempotency key are not concurrency control. If absent, remain preview/manual-handoff only. Use supported idempotency only when its real provider contract binds the same operation. Timeout or unknown outcome keeps the original attempt reserved: perform at most one authorized metadata-only reconciliation for that account/key ID, never re-create under another key name/account/transport. If a one-time value was lost, report `uncertain`/manual recovery; do not silently mint again or rotate/revoke the old credential.

Confirm creation from authoritative non-secret provider metadata for the approved account, key ID and scopes. Confirm storage separately via the store's metadata for the bound entry/version and protected operation. `created` is not `stored`, and an existing entry with a similar name is not proof this key was saved. An unchanged already-created/stored operation is a no-op, not another create; a genuinely requested replacement needs a new exact decision without silently revoking the old key. Storage failure after creation is partial completion; hold usage and report the remaining store/recovery step without the value. Do not automatically delete, revoke, overwrite or roll back an existing key; those are separate owner-authorized actions under the applicable destructive contract. If a secret is unexpectedly exposed, stop, avoid quoting it again and ask for the provider's supported revocation/rotation handoff; do not claim an exposed value can be made private by redacting a later report.

## Separately approved bounded test and reuse

Only test after the exact key is authoritatively created and stored, a protected handle/version is bound to this account and the owner requested the specific test. Preview one trusted HTTPS origin/resource/method, minimum non-sensitive payload, expected non-secret result, provider costs/quota and response/logging rules. A read may still be metered. Do not assume free access, use a mutable alias, allow arbitrary redirects, send client data, or test an endpoint selected by email. The host must inject the credential only into the approved origin/action and return sanitized non-secret evidence. No arbitrary parent agent receives the raw key or a bearer-capable “handle” in prose.

Require a fresh exact test approval. Missing cost/redirect/output controls or protected injection means manual handoff, not an HTTP request “to check.” A creation approval does not permit repeated tests. Timeout is uncertain; reconcile only by a supported authoritative non-secret observation, without retrying a metered operation or automatically paying. An authentication failure is not permission for a broader key, a new key, rotation, top-up or payment. A redirect to a new origin stops before following.

For a later independently requested job, the owner selects the exact resource operation and credential reference under that host's current permission rules; this does not inherit approval from onboarding. Do not use a different workspace/account/key because the selected one fails.

## Non-secret completion record and remaining coverage

Return only provider/origin, owner account reference, attempt/operation ID, provider key ID if non-secret, scope/lifetime metadata, store entry/version reference if safe, and separate `account_verified`, `activation`, `credential_created`, `credential_stored`, `test_requested`, `test_result` states. Omit raw keys, OTPs, proof headers, bearer URLs, cookies, request headers and sensitive account data. `not_requested`, `blocked`, `pending` and `uncertain` must stay distinct from success; no blanket `completed` if the requested usable-access outcome is unproven. Keep any non-secret record persistence separately authorized.

The source's useful goal is preserved as this review/handoff contract; its full autonomous API/compute provisioning, real private secret insertion/retrieval, resource allocation and provider adapter remain uncovered. Keep #134 open for those capabilities and maintainer placement/acceptance discussion. Normalized policy fixtures test decisions only, not service execution, secure storage, credential redaction, payment, concurrency or live E2E.
